# Wake trust model — who is trusted for what

2026-09-28 (rows 8, 9 and gap 3 updated the same day for A3b phase 4); **row 4, the verdict
table and gaps 6 to 8 updated 2026-10-06; rows 1, 4, 6–14 and the verdict table revised 2026-10-08 and 2026-10-09** for `WAKE-v1.md` §8.1 as amended and for Knotline v1;
**rows 1, 4, 6 to 8 and 10, the verdict table, rows 12 and 13 and gaps 9 and 10 updated 2026-10-08**
after an internal automated review (not an external one), for Zecboat 0.7.1 hardening 6 and 7. Covers Wake v1 (`zmap-wake` tag `wake-v1-draft-2026-09-28`), its use in the Zecboat
wallet (`zecboat_next` `8d9ba86`) and the issuance tool (`zecboat_mint_wake` `50eac78`).
Statements marked **[code]** were checked against the source on this date; the rest come from the
spec (`WAKE-v1.md`, `ZMAP-v0.5.md`) or are design intent.

**The claim Wake makes:** *the note in this wallet descends, through on-chain spends, from the
genesis output the issuer designated for this asset.* It does not claim ownership, value,
non-spending, or anything about who made the transfers.

## The table

| # | Party | Trusted for | If it lies, fails or disappears | Defence |
|---|---|---|---|---|
| 1 | **Zcash consensus, and what Ironwood's soundness rests on** | Every Ironwood Action sets `ρ_new = nf_old`, and every nullifier appears once in the pool | Wake means nothing | The base assumption. It is **not** "nothing on top of consensus" (said until 2026-10-08): `WAKE_HOP` leaves `nk` free, so one note has many valid proofs, and that a second *successor* still cannot exist rests on discrete log in Pallas, Poseidon collision resistance in `nk`, Sinsemilla binding for `NoteCommit` and `CommitIvk`, a sound post-NU6.2 Ironwood circuit, and nullifier uniqueness within the pool (`WAKE-v1.md` §9, "A free `nk`…"; not yet externally reviewed). Orchard-pool anchors are excluded: pre-NU6.2 Orchard proofs were unsound and nullifier sets are per pool (`WAKE-v1.md` §2). |
| 2 | **The Wake circuit, Halo 2 and the Orchard gadgets** | Soundness: a valid proof implies the relation in `WAKE-v1.md` §4 | **Forgery**: a proof of descent that isn't true | Negative and sabotage tests, a constraint listing, a diff against Orchard. Pinned versions include the `halo2_gadgets` 0.5.0 fix of the variable-base scalar multiplication soundness bug (its CHANGELOG, "Fixed") and `orchard` 0.15.3's canonical proof-size check (GHSA-2x4w-pxqw-58v9). (Until 2026-10-09 this cell cited "CVE-2026-54496", an identifier found in no changelog or CVE index; withdrawn.) **External review is still required (§11.4). This is the one row where a failure is silent.** |
| 3 | **The issuer** (holder of `ik`) | Naming the genesis outputs and minting only what it declares | Extra units, or a genesis pointing somewhere else | Manifest signed by `ik`; pin, close and genesis list on chain; issuer viewing key published; the audit checks count, closure and value (checks 8, 9, 14). **[code]** The wallet shows `GenesisMismatch` (Broken) when a lading's genesis differs from the one the manifest names. |
| 4 | **The chain oracle** used by the verifier | Answering "is this root real at height h" and "what is `cmx` at this output" | It can hide or fake roots, making a unit look unproven or, if faked consistently with a forged proof, look proven | **[code]** Only an oracle marked `FullNode` can produce **Verified**, and only a zebrad whose URL parses as loopback is marked so (`oracle::is_local_url`: `http://` only, no userinfo, an IP literal in `127/8` or `::1`, or the literal `localhost`, then connected to loopback addresses only; one parse serves the trust decision and the connection, so v4-mapped literals, odd ports and whitespace are refused by both since 2026-10-09). **Stated limit:** whatever listens on that port of this machine counts as the holder's node; a squatter or a tunnel is not detected. Every other answer (lightwalletd/zainod, or a zebrad reached over a network) is `ServerAsserted` and gives at most **Checked via provider**, never Verified (`WAKE-v1.md` §8.1). The checks that need no oracle run first, so a forged lading fails as forged and the oracle is never asked about heights a forger chose. Anchors must be 100 blocks deep (`MIN_DEPTH`, a policy value; basis in `WAKE-v1.md` §8); under a server the tip, and so the depth, are the server's word. A transaction returned by any server, zebrad included, is checked against the id it was asked for. Only "no such transaction" (RPC error −5) from a zebrad on this machine means "not on chain"; any other failure, from any source, yields "could not be checked", never Broken. With the chain source set to "my own node only", a silent node is never replaced by the provider. |
| 5 | **The network path** to nodes and servers | Nothing | Can read or alter traffic. Today zainod is plain HTTP on the LAN; zebrad RPC is plain HTTP on localhost. | Row 4's rules. Spends need keys and are checked by the network, so funds cannot be taken this way. Planned: warn on non-HTTPS endpoints; bind to localhost where possible. |
| 6 | **The sender** of a unit | Delivering the lading, and writing true knots | If it withholds or writes a wrong knot, the unit shows **No lading**: unproven, not forged | The memo's `consignment_hash` commits to the lading; a later lading must hash to it. **[code]** A sender chains its knot to a key memo only when the lading it extends was itself rebuilt from that line (`KNOTLINE-v1.md` §4), so a bad knot ends the line instead of being extended by every later holder. |
| 7 | **A drop-box**, only one the holder names (`https://` or a shared `file://` folder); there is none by default and zecboat.com runs none | Availability only | It can withhold, and it sees the network address of both sides. It cannot read ladings, because they're sealed to the recipient, and it cannot frame a unit (a stranger's transaction can try; row 12) | **[code]** A fetched lading must open with the recipient's keys **and** hash to the memo's value, or it is discarded and nothing is stored. A bad drop-box leaves a unit at *No lading*, never *Broken*. The hash used as the filename is 64 hex characters (validated when the memo is parsed). First delivery wins; a squatter would need the hash before the sender uploads. |
| 8 | **zecboat.com** (registry metadata and artwork host) | Availability of **artwork and metadata**. **It also learns something**: when a holder opens an item, its asset id and the holder's network address | Since A3b phase 4 (2026-09-28) it is **not needed to validate** a registered collection: the manifest is read from the chain. Without it, artwork cannot be shown (only its hash is on chain). It is no drop-box | Manifests are checked against a pinned key, or (phase 4) against the registered key after a passed audit; artwork is checked against its hash. **[code]** Since 2026-10-08 artwork is requested only for an item opened in the session (until then every open of the item list sent every held asset id), metadata, artwork and manifests come only from the configured registry by asset id through one client (`https`, no redirects, 30 s, bodies bounded: metadata 256 KB, artwork 8 MB, manifests 1 MB; since 2026-10-09 for artwork and manifests), and a host named by a memo's `metadata_uri` is never contacted. Proven 2026-09-28: with zecboat.com replaced by a dead address, Lagos #007 is still Verified. **Verification never asks zecboat.com (2026-10-09):** a pinned collection's manifest comes from the chain (the registry audit's copy of the close) or from a copy built into the wallet, and the two pre-v1 manifests are built in; from hardening 13 to hardening 16 on 2026-10-09 the pinned path asked the website first and failed when it failed, which was the drop-box mistake and is withdrawn. If the site is deleted, artwork and human-readable metadata are lost and nothing else. |
| 9 | **The Zecboat Registry** (its key is pinned in the wallet) | Since phase 4: **the root of trust for registered collections.** A collection found there **and passing all 17 audit checks** is trusted like a pinned one | It can list or omit collections. A registration alone proves only that the `ik` holder registered that viewing key; trust comes from the audit | **[code]** Trusted only on a complete, passed audit that kept the manifest etched on chain and lists the unit (`pick_listing`); a registered but unchecked collection shows grey "not checked yet", never a red "not issued". The audit is to a block: re-checking confirms nothing was issued since. **Since 2026-10-09:** the Registry lists impostors too, by design: anyone can register a collection with a known name under a key of their own, and a 32-bit key fragment is ground in under two hours (review, session 4, Issue A). A registry-only collection is therefore shown as *registered*, with a long key fingerprint and a look-alike warning when its name matches a pinned one, and is **never green**; green needs a key pinned in the wallet (`PINNED_V1`: Lagos Post Card, Happy Birthday Zcash 10, Barcelona Post Card 2026) and a lineage Verified against the holder's own node. |
| 10 | **The recipient's own wallet software** | Running every check honestly and reporting which one failed, and not losing a send it has signed | A bad build could show anything | Published build hashes; open source; the badge (Verified / Checked via provider / Unverified / No lading / Broken) never collapses "unproven" into "forged", and the green issuance badge appears only beside a lineage that holds. **[code]** Once a signed transaction is stored, nothing reports the send as failed (the wallet broadcasts what it stored; a "failed" invited a retry that spent the carrier twice). Reproducible builds are **not** yet in place. |
| 11 | **The holder**, when selling | Nothing | Can prove a note and then spend it before the buyer is paid. "One successor" is guaranteed; "one claimant" is not | **Market rule, not code:** `SETTLEMENT_RULE.md`. The unit moves first; the buyer pays (or escrow releases) only when the buyer's own wallet shows Verified against the buyer's own zebrad. Every seller trick shows as something other than Verified. |
| 12 | **A stranger who sends you a transaction** (anyone who knows the address) | Nothing | Can send a copy of a unit, with a copied memo and a lading of its own. Until 2026-10-08 that lading displaced the genuine one: the genuine unit showed Broken and could not be sent | **[code]** A lading is stored only after the checks that need no oracle pass (hash, canonical form, every proof, the chain rule, the note's `ρ`); one that fails is recorded against the copy it came with, as rejected, and that copy alone shows Broken. A lading is chosen by its carrier, never by asset id: the one the carrier's memo commits to by hash, or, with no hash, only a lading that arrived with that very note (`received_note_id`); until 2026-10-09 it was the newest for the asset that ended at the note's `ρ`, which is public, so a copy could still displace a unit at its first holder. Every carrier is verified and the best result shown, with every copy's own state listed when there are several; the send spends the copy whose lineage checks out best, never a broken one beside a sound one. A copy reads as unproven or, with a failed lading, broken, and never takes the green issuance badge (row 10). **Cost a stranger can impose (2026-10-09):** a carrier with a key memo made the wallet walk a 512-knot line of the stranger's choosing on every pass, waited on by sends. Now a walk runs automatically only for an asset a pinned manifest or a passed audit names, in a background job with a time and byte budget; the send collects only the unit being sent; a failed line backs off with a doubling delay kept in the database. Since hardening 16 an asset counts as known only when a manifest the wallet holds and has verified lists it; each walk has its own budget; a send of a unit whose memo commits to an uncollected lading is refused rather than offered unproven, and several copies are sent only when exactly one checks out against the manifest's genesis. |
| 13 | **Whoever holds a viewing key** of an account: the sender's own OVK, or an issuance account's published UFVK | Nothing | Knot and key-memo outputs can be read with the **sender's** OVK, so a holder's exposed viewing key reveals the knot keys they sent. Units sent from an issuance account whose viewing key is published expose the buyer | Decided 2026-10-08: the sender keeps its OVK on those outputs (a wallet restored from seed rebuilds its sent History from them; `KNOTLINE-v1.md` §10 says MAY discard). Rule for issuers: never send units from the published issuance account. **Genesis outputs are the exception:** they are sent from the issuance account by construction, so their recipient addresses are readable by anyone holding the published key; an issuer MUST mint to its own treasury (ZMAP §7.4, 2026-10-09). The sender's own wallet database also keeps every key memo and knot it sent in plaintext (sent-note memos), a second route to those keys besides the OVK. |
| 14 | **Whoever controls the process environment** | Nothing | Can point the wallet at a different node, provider, registry or plugin binary | **[code]** A release build reads `ZECBOAT_PROVIDER`, `ZECBOAT_REGISTRY`, `ZECBOAT_ZEBRAD_RPC`, `ZECBOAT_DROPBOX`, `ZECBOAT_LADING_IN_MEMOS`, `ZECBOAT_TRANSPARENT_SCAN`, `ZECBOAT_WAKE_TRACE`, `HOME` and `PATH` (for `age-plugin-yubikey`). `ZECBOAT_WAKE_MANIFEST` and `ZECBOAT_PINNED_V1` are compiled out of release builds. A fake JSON-RPC node on another loopback port, named by `ZECBOAT_ZEBRAD_RPC`, is `FullNode` (row 4's stated limit) and can make a lading of real proofs over invented anchors read Verified; since 2026-10-09 the Verified badge names the address it trusted. Manifests from a substituted registry are still signature-checked. Stated, not detected: the same precondition as rows 10 and 13. Also: `reqwest` clients honoured `HTTP(S)_PROXY`/`ALL_PROXY` until 2026-10-09; the registry, drop-box and broadcast clients now ignore proxy variables (gRPC and the node oracle never used them). `ZECBOAT_DROPBOX` is accepted only as `https://` or `file://`. |

## What a verdict means

| Badge | Means | Depends on rows |
|---|---|---|
| **Verified** | Proofs valid, chain rule holds, anchors ≥100 deep, checked against a node on this machine, genesis matches the issuer's signed manifest | 1, 2, 3, 4 (own node), 10 |
| **Checked via provider** | The same five checks pass, but the chain's answers came from a server the holder does not run. The report names that server and must not look like Verified in wording, colour or mark | 1, 2, 3, 4 (server), 10 |
| **Unverified** | Could not be checked right now. Either the checks that need no chain source passed (proofs, chain rule, final note) and the chain's answers could not be obtained or the anchors are not yet deep enough, or there is no trusted manifest to name the genesis. Says nothing either way about forgery | 1, 2 |
| **No lading** | Nothing to check yet | none; says nothing about the asset |
| **Broken** | Evidence of forgery or tampering: a bad proof, a broken chain, genesis not on chain, a hash mismatch on a held lading, the wrong final note, or a genesis mismatch | whoever made the lading |

## Known gaps (as of 2026-09-28; 9 and 10 added 2026-10-08)

1. **Row 2 is unreviewed.** It is the only row where a failure isn't visible.
2. **Row 11: settlement is a written rule (`SETTLEMENT_RULE.md`), not enforced by code.** Seller protection needs an escrow; a one-transaction swap is not designed.
3. ~~Lagos Post Card can't reach Verified lineage yet.~~ **Closed 2026-09-28 by A3b phase 4:** once
   Lagos is checked in Collections, its units get the issuer badge and a genesis from the chain,
   with no `PINNED_V1` line.
4. **Row 5:** plain-HTTP endpoints with no warning.
5. **Row 10:** builds are not reproducible; users can compare hashes but can't rebuild to match.
6. **Privacy, not trust:** a v1 lading shows its recipient the lineage's nullifiers, which link
   the transfers. A lading must never be published in a form anyone but the note's holders can
   read (`WAKE-v1.md` §7.3); v1.5 and v2 reduce what the recipient learns.
7. **Knotline v1 is unreviewed** (`KNOTLINE-v1.md`). It writes each hop proof to the chain sealed
   under a one-time key. Integrity does not rest on it (a wrong knot cannot produce a lading that
   matches the transfer's hash), but its privacy claims (§6 and §10 there) have been checked only
   by its authors, and a knot cannot be withdrawn.
8. **A light server sees what a wallet asks for.** A wallet without its own node asks its server
   for the transactions and tree states of a lineage. The reference fetches whole blocks to blur
   which transaction was wanted; that is no cover against the server itself, which sees every
   transaction's action count in the blocks it serves and can pick the 14-action knot transfer
   out of each (measured 2026-10-09). Through a provider, a walk reveals the item's transfer
   chain. A uniform transfer shape is planned for 0.7.2; an anonymising transport is not built.
   The cover holds against an honest server only: one that answers selectively can still learn
   which transaction was wanted (`KNOTLINE-v1.md` §7).
9. **A knot transfer has a recognisable shape** (14 actions, about 47 KB). The encryption hides
   what a knot says, not that one was sent; with few users, that can mark a resale.
10. **Row 4's loopback rule cannot see a squatter** on the node's port or a tunnel; cookie
    authentication to the node is not built.

## Out of scope for Wake

Ownership, price, and what an asset means (the overlay's job); crossing the Orchard→Ironwood
bundle boundary (v2); the right to spend (Zcash's spend authorization, untouched by Wake).
